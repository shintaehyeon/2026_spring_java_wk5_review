# Spring Week 5 프로젝트 코드 해설 리포트

이 문서는 **이 저장소의 실제 코드**를 처음부터 끝까지 읽는 공부 자료다. 각 파일을 왜 만들었는지, 입력이 어떻게 처리되고 어디에 결과가 나오는지 설명한다. 기본 단어는 [용어장](공부내용-스프링-용어암기.md), IntelliJ 실행 문제는 [오류 보고서](공부내용-IntelliJ-Gradle-오류보고서.md)를 함께 본다.

## 0. 전체 흐름: 이 프로젝트의 알고리즘

여기서 알고리즘은 복잡한 수학 공식이 아니라 **입력 → 처리 → 출력의 순서**다.

~~~text
브라우저가 HTTP 요청을 보냄
  → Spring MVC가 URL과 GET/POST/PUT/DELETE를 보고 Controller 메서드를 고름
  → 간단한 계산: Controller에서 계산
  → 게시판: Controller → Service → Repository → H2 DB
  → Controller가 HTML 화면 이름 또는 데이터 응답을 반환
  → 브라우저에 결과 표시
~~~

Entity는 이 흐름에서 다루는 데이터의 모양이다. Controller 다음에 반드시 실행되는 별도 단계가 아니다. BUILD SUCCESSFUL은 빌드/동기화 성공, Started Week5Application은 앱 실행 성공, 브라우저 결과는 실제 HTTP 동작 확인이다. 셋을 구분한다.

## 2. 앱 시작과 설정

[Week5Application.java](../src/main/java/com/example/week5/Week5Application.java)의 main은 Java 프로그램의 시작 메서드다. SpringApplication.run을 호출하면 Spring Boot가 앱을 준비한다. @SpringBootApplication이 있는 com.example.week5 아래에서 컨트롤러와 서비스 등을 찾는다. Spring이 관리하는 객체는 Bean, 이를 만들고 연결하는 곳은 Spring 컨테이너다.

[build.gradle](../build.gradle)의 Java toolchain 17은 이 프로젝트가 Java 17로 빌드된다는 뜻이다. dependencies의 webmvc는 HTTP 요청 처리, thymeleaf는 HTML 템플릿, data-jpa는 DB 접근, h2는 임시 DB를 제공한다. build.gradle은 앱의 main 파일이 아니므로 이 파일을 Current File로 실행하지 않는다.

[application.properties](../src/main/resources/application.properties)의 server.port=8081은 브라우저 주소가 http://localhost:8081/임을 뜻한다. localhost는 내 컴퓨터이고, 8081은 앱의 포트다. H2 메모리 DB는 앱을 끄면 게시글이 사라진다. create-drop은 앱 실행 시 테이블을 만들고 종료할 때 제거하는 학습용 설정이다.

## 3. 계산 예제: Controller에서 HTML까지

[PracticeController.java](../src/main/java/com/example/week5/controller/PracticeController.java)의 @Controller는 화면을 선택할 수 있는 컨트롤러라는 표시다. @GetMapping은 GET 주소를 Java 메서드에 연결한다. 브라우저 주소창에 주소를 입력하면 보통 GET 요청을 보낸다.

| 주소 | 메서드 | 입력 → 처리 → 결과 |
|---|---|---|
| / | home() | index라는 화면 이름 반환 → templates/index.html |
| /test | test() | 글자 OK를 응답 본문으로 보냄 |
| /practice/param/hello | pathVariable() | 경로의 hello를 word로 받음 → 받은 글자 표시 |
| /practice/add?a=2&b=3 | add() | 2와 3을 더함 → HTML에 결과 5 |
| /practice/concat?a=Java&b=Spring | concat() | 문자열을 붙임 → JavaSpring |
| /practice/multiply?a=2&b=3 | multiply() | 2와 3을 곱함 → HTML에 결과 6 |
| /practice/redirect | redirect() | 브라우저를 /boards로 다시 이동 |

### 더하기 코드를 손으로 추적하기

~~~java
@GetMapping("/practice/add")
public String add(@RequestParam("a") int a,
                  @RequestParam("b") int b,
                  Model model) {
    model.addAttribute("title", "두 숫자 더하기");
    model.addAttribute("result", a + b);
    return "practice/result";
}
~~~

1. 물음표 뒤 a=2&b=3은 쿼리 파라미터다. @RequestParam이 각 값을 받고 int 숫자로 변환한다.
2. a+b가 5가 된다. Model에 title과 result라는 이름으로 값을 담는다.
3. 반환한 practice/result는 숫자 5가 아니라 **화면 이름**이다. Spring이 templates/practice/result.html을 사용한다.
4. 그 HTML의 th:text가 Model에 담긴 값을 표시하므로 화면에서 “결과: 5”를 본다.

b를 빼거나 숫자 대신 글자를 넣으면 필요한 int 값으로 만들 수 없어 400 Bad Request가 날 수 있다. 그때는 계산식보다 입력 주소를 먼저 확인한다.

### 페이지 응답과 REST 응답 비교

- 페이지 곱하기: PracticeController.multiply()가 Model에 6을 담고 result.html을 반환한다. 제목과 링크가 있는 HTML 페이지가 보인다.
- REST 곱하기: [PracticeRestController.java](../src/main/java/com/example/week5/controller/PracticeRestController.java)의 @RestController 메서드가 int 6을 반환한다. /api/practice/multiply?a=2&b=3에는 숫자 6만 보인다. HTML 파일을 쓰지 않는다.
- @Controller 안의 @ResponseBody도 반환값을 화면 이름 대신 응답 본문으로 보낸다. /test에서 OK 글자만 보이는 이유다.

int 두 개의 +는 산술 덧셈이고, String 두 개의 +는 글자 이어 붙이기다. 먼저 매개변수의 타입을 보면 결과를 예측할 수 있다. return "redirect:/boards"는 HTML 파일 이름이 아니라 브라우저에게 새 주소로 이동하라는 뜻이다.

## 4. 게시판 구조와 생성자 주입

HTML 주소 /boards와 REST 주소 /api/boards는 **같은 BoardService와 DB**를 사용한다. 응답 모양만 다르다.

| 구성 | 실제 역할 |
|---|---|
| [BoardController.java](../src/main/java/com/example/week5/controller/BoardController.java) | HTML 화면용 URL·폼 입력·Model·리다이렉트 |
| [BoardRestController.java](../src/main/java/com/example/week5/controller/BoardRestController.java) | JSON API용 URL·요청 본문·상태 코드 |
| [BoardService.java](../src/main/java/com/example/week5/service/BoardService.java) | findAll/findById/create/update/delete 기능의 약속인 interface |
| [BoardServiceImpl.java](../src/main/java/com/example/week5/service/impl/BoardServiceImpl.java) | 약속을 실제로 구현. impl은 implementation의 약자 |
| [BoardRepository.java](../src/main/java/com/example/week5/repository/BoardRepository.java) | JpaRepository를 상속해 저장·조회·삭제 |
| [Board.java](../src/main/java/com/example/week5/entity/Board.java) | id·title·content를 가진 Entity |

BoardController는 BoardService를 new로 직접 만들지 않고 생성자에서 받는다. Spring 컨테이너가 @Service가 붙은 BoardServiceImpl 객체를 찾아 넣는다. 이것이 **의존성 주입(DI)** 중 생성자 주입이다. BoardServiceImpl도 같은 방식으로 BoardRepository를 받는다. private final 필드는 한 번 연결된 객체를 다른 것으로 다시 대입하지 못하게 한다.

BoardRepository의 JpaRepository<Board, Long>은 “Board 데이터를 Long ID로 관리한다”는 뜻이다. findAll, findById, save, deleteById 등을 사용할 수 있다. Board의 @Entity는 JPA 관리 대상, @Id는 기본키(PK), @GeneratedValue는 ID를 만드는 방식을 나타낸다.

## 5. 게시글 작성 알고리즘

~~~text
GET /boards/new
  → BoardController.createForm()
  → board/create.html 표시

폼에 제목="첫 글", 내용="내용" 입력 후 저장
  → POST /boards
  → BoardController.create(title, content)
  → BoardServiceImpl.create(title, content)
  → new Board(title, content)
  → BoardRepository.save(board)
  → H2 DB에 저장되고 id 생성
  → redirect:/boards
  → 브라우저가 목록을 다시 요청
~~~

[create.html](../src/main/resources/templates/board/create.html)의 input name="title"과 textarea name="content"가 @RequestParam String title, content의 이름과 맞아야 한다. required는 브라우저에서 빈칸 제출을 막도록 돕지만 서버의 완전한 검증 로직을 대신하지 않는다.

### 목록·상세·수정·삭제

| 동작 | URL·방식 | Controller → Service → Repository | 결과 |
|---|---|---|---|
| 목록 | GET /boards | list() → findAll() → findAll() | Model의 boards → board/list.html |
| 상세 | GET /boards/1 | detail(id) → findById(id) → findById(id) | Model의 board → board/detail.html |
| 수정 화면 | GET /boards/1/edit | editForm(id) → findById(id) | board/edit.html에 기존 값 표시 |
| 수정 제출 | POST /boards/1/edit | update(id, title, content) → 찾기 → board.update → save | /boards/1로 이동 |
| 삭제 | POST /boards/1/delete | delete(id) → 찾기 → deleteById | /boards로 이동 |

숫자 1은 실제 게시글 ID로 바꿔야 한다. @PathVariable Long id가 URL의 숫자를 받는다. ServiceImpl.findById()는 글이 없으면 orElseThrow로 404 Not Found 예외를 만든다. 삭제도 먼저 findById를 호출해 없는 글을 구별한다.

일반 HTML 폼은 이 예제에서 수정·삭제도 POST로 보낸다. 아래 REST API는 수정에 PUT, 삭제에 DELETE를 쓴다. 같은 “수정” 작업이라도 브라우저 폼과 REST가 받는 HTTP 방식은 다를 수 있다.

### HTML 파일의 표시 규칙

- [list.html](../src/main/resources/templates/board/list.html): th:if로 빈 목록 문구를 표시하고 th:each로 글마다 제목 링크를 만든다.
- [detail.html](../src/main/resources/templates/board/detail.html): Model의 board에서 제목·ID·내용을 읽고 수정·삭제 주소에 ID를 넣는다.
- [edit.html](../src/main/resources/templates/board/edit.html): th:value와 th:text로 기존 제목·내용을 입력칸에 채운다.
- [index.html](../src/main/resources/templates/index.html): 실습 링크 메뉴다. 모든 결과를 첫 화면에 한꺼번에 보여주지 않는다.

## 6. REST 게시판 코드 읽기

[BoardRestController.java](../src/main/java/com/example/week5/controller/BoardRestController.java)의 BoardRequest와 BoardResponse는 record로 만든 **데이터 전달 객체(DTO)**다. 요청에는 title·content, 응답에는 id·title·content가 들어간다. BoardResponse.from(board)가 Entity의 값을 응답 객체로 옮긴다.

| 요청 | 메서드 | 결과 |
|---|---|---|
| GET /api/boards | list() | Board 목록을 BoardResponse 목록으로 바꿔 JSON 배열로 보냄. 빈 목록은 [] |
| GET /api/boards/1 | detail(id) | 글 하나를 JSON으로 보냄 |
| POST /api/boards | create(@RequestBody BoardRequest) | JSON을 받아 저장. 201 Created, Location 헤더와 글 데이터 |
| PUT /api/boards/1 | update(id, @RequestBody BoardRequest) | JSON의 값으로 수정 후 글 데이터 |
| DELETE /api/boards/1 | delete(id) | 삭제 성공 시 204 No Content |

@RequestBody는 **브라우저/클라이언트 → 서버**의 본문을 받고, @ResponseBody와 @RestController는 **서버 → 브라우저/클라이언트**의 응답 본문을 보낸다. ResponseEntity는 HTTP 상태 코드·헤더·본문을 함께 정한다.

목록의 findAll().stream().map(BoardResponse::from).toList()는 Board를 하나씩 BoardResponse로 바꾼 뒤 목록으로 모은다. 여기서 소문자 map은 변환 메서드다. 키와 값을 저장하는 대문자 Map 자료구조와 다르다. 실제 계산 컨트롤러는 Map 대신 Model에 값을 직접 담는다.

## 7. 꼭 알아야 할 코드 단어

| 단어 | 한 문장 의미 |
|---|---|
| package / import | 클래스의 소속 / 다른 패키지 클래스를 쓰기 위한 선언 |
| class / interface / implements | 객체 설계 / 기능의 약속 / 약속의 구현 |
| public / private / protected | 코드에 접근할 수 있는 범위 |
| new / 생성자 | 새 객체를 만듦 / 만들 때 필요한 값을 받음 |
| final | 필드를 다른 객체로 다시 대입하지 못하게 함 |
| void / return | 반환값이 없음 / 결과를 호출한 쪽에 돌려줌 |
| Long / List<Board> | 게시글 번호의 객체 타입 / 게시글 여러 개의 목록 |
| @Override | 약속한 메서드를 구현·재정의한다는 표시 |
| @RequestParam / @PathVariable / @RequestBody | 파라미터 / URL 경로 값 / 요청 본문을 받음 |
| Model / Thymeleaf | 화면에 건넬 데이터 / 그 데이터를 HTML에 끼워 넣음 |
| JPA / H2 | Java 객체와 DB를 연결하는 규칙 / 여기서 쓰는 임시 DB |
| @Entity / @Id / @GeneratedValue | DB 데이터 클래스 / 기본키 / 키 생성 방법 |
| @Test / MockMvc | 자동 테스트 표시 / 브라우저 없이 HTTP 요청을 흉내 냄 |

**Map과 Model:** Map은 Java의 키→값 자료구조, Model은 HTML 템플릿으로 값을 건네는 Spring MVC 객체다. 예제와 암기 문제는 [용어장](공부내용-스프링-용어암기.md)에 있다.

## 8. 테스트 코드는 무엇을 확인하나?

[BoardFlowTest.java](../src/test/java/com/example/week5/BoardFlowTest.java)는 @SpringBootTest로 Spring 설정을 사용하고 MockMvc로 요청을 테스트 안에서 흉내 낸다. 테스트 성공과 실제 브라우저를 직접 눌러 본 것은 구분한다.

- 첫 테스트: 게시판 목록 → 폼으로 글 생성 → 상세 → 수정 → REST 조회에서 수정값 확인 → 삭제 → 없는 글 404.
- 둘째 테스트: 페이지 더하기 → REST 곱하기 6 → REST 글 생성 201 → 수정 → 삭제 204 → 없는 글 404.
- andExpect는 예상한 결과를 검사한다. status는 HTTP 상태, view는 선택한 화면, jsonPath는 JSON 값, redirectedUrl은 이동 주소를 확인한다.

## 9. 공부 순서와 셀프 점검

1. /practice/add?a=2&b=3을 열고 a, b, result, return을 PracticeController에서 손으로 표시한다. result.html의 표시 부분을 찾는다.
2. /practice/multiply?a=2&b=3과 /api/practice/multiply?a=2&b=3을 비교해 HTML과 데이터 응답의 차이를 말한다.
3. /boards에서 글 하나를 만들고 create.html의 name → BoardController.create → BoardServiceImpl.create → BoardRepository.save → Board.id 순서로 파일을 연다.
4. /boards와 /api/boards에서 같은 글을 보고, HTML과 JSON의 차이를 말한다.
5. 수정·삭제할 때 URL의 ID가 어느 메서드에 들어가고 어떤 Repository 메서드가 호출되는지 찾는다.
6. BoardFlowTest의 perform은 무엇을 요청하고 andExpect는 무엇을 검사하는지 한 줄씩 설명한다.

| 답을 가리고 물어볼 질문 | 정답 확인 |
|---|---|
| a=2&b=3은 어디에서 받나? | PracticeController.add의 @RequestParam |
| 더한 5는 어떻게 HTML에 들어가나? | Model의 result → result.html의 th:text |
| REST 곱하기에서 숫자만 나오는 이유는? | @RestController가 int를 응답 본문에 반환 |
| 폼의 제목은 어떤 이름으로 전송되나? | name="title" |
| 새 게시글의 ID는 언제 생기나? | Repository로 저장할 때 JPA/DB가 생성 |
| 글이 없을 때 404는 어디에서 결정하나? | BoardServiceImpl.findById의 orElseThrow |
| 두 게시판 컨트롤러는 같은 DB를 보나? | 같은 BoardService와 Repository를 사용 |
| BUILD SUCCESSFUL이면 서버도 켜졌나? | 아니다. Run 창의 Started Week5Application도 확인 |

**학습 완료 기준:** 더하기와 게시글 작성 과정을 각각 **입력 → Controller → 처리 → 결과** 순서로, 표를 보지 않고 설명할 수 있다.

## 10. IntelliJ에서 한 줄씩 실제 실행을 보는 방법

코드를 눈으로만 읽으면 a와 b가 어디서 들어오는지 헷갈릴 수 있다. **중단점(breakpoint)**을 쓰면 요청이 해당 줄에 도착했을 때 앱이 잠시 멈추고 변수 값을 보여준다.

1. 실행 중인 Week5Application이 있으면 Run 창의 Stop 버튼으로 멈춘다. 같은 8081 포트에서 Run과 Debug를 동시에 시작하지 않는다.
2. PracticeController.java의 add() 메서드에서 model.addAttribute("result", a + b); 줄 **왼쪽 여백**을 클릭해 빨간 점을 만든다.
3. Week5Application.java의 main 옆 초록 화살표를 눌러 **Debug**로 시작한다.
4. 브라우저에서 http://localhost:8081/practice/add?a=2&b=3을 연다. IntelliJ가 빨간 점에서 멈추면 Variables 창에서 a=2, b=3을 확인한다.
5. Debug 창의 **Step Over**로 다음 줄까지 진행한 뒤 **Resume**으로 계속 실행한다. 브라우저에 결과 5가 나오는지 본다.
6. 다음에는 BoardController.create()와 BoardServiceImpl.create()에 중단점을 놓고 게시글을 저장해, Controller에서 Service로 이동하는 순서를 직접 관찰한다.

중단점에서 앱이 멈춘 동안 브라우저는 응답을 기다리는 상태다. 오류가 난 것이 아니므로 Resume을 눌러 마무리한다.

## 11. 이 예제의 범위

이 프로젝트는 복습용 최소 예제다. 로그인, 권한 검사, 충분한 서버 입력 검증, 영구 DB, 목록 페이지 나누기는 없다. 앱을 껐다 켜면 H2 메모리 DB의 게시글이 없어지는 것은 이 설정에서 예상되는 동작이다.
